# Data preprocessing and normalisation

`raw -> clean -> normalized`, each stage reproducible and recorded. Code: `src/wxrisk/prep/`, command: `scripts/40_prep.py`.

| Stage | What happens | Output |
|---|---|---|
| raw | downloads, untouched; fingerprinted by `data.lock.json` | `$WXRISK_DATA/...` |
| clean | types, key normalisation, rules for missing values, deterministic row order | `clean/<table>.parquet` + `<table>.prep.json` |
| normalized | scaling parameters fitted on the **training period only**, applied as a pure function | `clean/<table>.norm.json` |

## Missing values and placeholders

Who defines a value decides how it is treated; the full procedure, and one entry per rule with its evidence, is in
[`docs/CLEANING_REGISTER.md`](CLEANING_REGISTER.md) (generated by `python scripts/40_prep.py register` from the rules, the build records and
`scripts/41_cleaning_evidence.py`). In short:

| Origin | Example | Treatment |
|---|---|---|
| provider-documented | negative premium = refund; 9999 = not reported; depth relative to grade | follow the provider |
| provider-placeholder | "99XX" values (999 in depth) | null + `_missing` flag, found by a spike scan of all numeric columns |
| undocumented code | depth 0, foundation '0', construction date 1492-10-12 | spike + profile test; null + flag |
| entry error | years 0001/1010, elevation difference -9986, depth 6000 | the value is nulled, never the row |
| structural | building coverage 0 (contents-only policy) | kept |
| unusable for every analysis | no event date | row dropped and counted (0 rows today) |

Missing location keys (null `censusGeoid`) are kept and flagged: the rows are real policies and claims and state totals need them; analyses that need a
block group filter on `geoid_missing`. Never stringify a key before that check. Engine differences that motivated this (pandas / Polars 2.0 / DuckDB 2.0):
`groupby` drops null keys in pandas and keeps them in Polars/DuckDB; `merge` matches null to null in pandas but not in Polars/DuckDB; a NaN in Polars is *not* null.

Imputation never enters a clean table (fitted values would be indistinguishable from observations). It is a feature-stage choice that needs a masked-value
validation and a train-only fit.

Adding a rule: put it in `specs.py`, add its entry to `register.py` (the test fails otherwise), run `scripts/41_cleaning_evidence.py` if it needs new evidence.

## Scaling

A separate stage after cleaning: `prep/scaling.py` (feature plans fitted on training rows, group-aware statistics, supervised bins, target transforms with the inverse) and the decisions with their evidence in [`docs/SCALING_PLAN.md`](SCALING_PLAN.md) (`python scripts/40_prep.py scaling-plan`). The older `prep/normalize.py` is the minimal version used for the policies table.

## Reproducibility guarantees

- Output rows are totally ordered (sorted by every output column), so the result does not depend on input row order or thread count.
- The sidecar holds the input's content hash, the spec hash (rules + cleaning version), the output's content hash and the row accounting.
  It contains no time or machine data, so two builds from the same raw file give identical sidecars.
- `40_prep.py verify` re-derives the table from the raw file into a temp dir and compares content hashes (not bytes: parquet writers differ).
- Cleaning uses only string, integer, date and comparison operations, so it is exact across platforms. Normalisation parameters are
  rounded to 12 significant digits; `apply` is bit-identical on one platform and agrees to ~1e-12 across platforms (`log1p` can differ in the last bit).
- Normalisation `fit` needs an explicit training mask and stores it; `apply` refuses parameters edited after fitting.

## Adding a table

Add a `TableSpec` to `prep/specs.py` (one `Col` per column; declare the rule for every column that can be missing), run
`python scripts/40_prep.py build <name>` then `report <name>`, and put the dropped/nullified counts in the stage's *Caveats* in `RESULTS.md`.
